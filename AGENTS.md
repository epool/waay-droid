# AGENTS.md — Wáay (Kotlin Multiplatform)

Single source of instructions for every coding agent and human contributor.
`CLAUDE.md` only imports this file. The **constitution** (`.specify/memory/constitution.md`) is the
authoritative source for principles; when it and this file disagree, the constitution wins and this
file must be updated.

## 1. What this project is

**Wáay** ("wáay" ≈ sorcerer in Yucatec Maya) is a "magic cards" mind-reading game, rebuilt from
scratch as a state-of-the-art Kotlin Multiplatform (KMP) app. The legacy 2014 Android-only app lives
on `master`.

- The player thinks of a number in `1 … 2^N − 1`. The app shows N cards. Card *i* lists every number
  whose bit *i* is set. The player answers yes or no for each card, and the app reveals the number
  (the sum of `2^i` over the "yes" cards).
- v1 scope (spec 001):
  - parity with the original;
  - randomized card order and shuffled numbers within each card, decoded through a hidden bit map;
  - card count from 3 to 7;
  - text-to-speech;
  - English and Spanish;
  - persisted settings.
- Platforms in v1:
  - **Android**: Jetpack Compose, Material 3;
  - **iOS**: SwiftUI.
- Later specs, likely in this order:
  - web (Kotlin/Wasm);
  - desktop;
  - a Compose Multiplatform `sharedUI` module;
  - migration to Swift export.

## 3. Spec-driven development (mandatory workflow)

No production code is written without an approved spec, plan, and task list.

### The loop (per feature)

Steps marked ⛔ are **review gates**: the agent stops and waits for the human.

| Step | Command | Output | Gate |
|---|---|---|---|
| 0 | `/speckit-constitution` | Principles. Run only when they change. | ⛔ |
| 1 | `/speckit-specify <what & why, no tech>` | Creates branch `NNN-slug` off `kmp` and `specs/NNN-slug/spec.md`. | |
| 2 | `/speckit-clarify` | Asks up to 5 questions and writes the answers into the spec. | ⛔ |
| 3 | `/speckit-plan <tech constraints>` | `plan.md`, `research.md` (ADRs + version matrix with sources), `data-model.md`, `contracts/`, `quickstart.md`. | |
| 4 | `/speckit-tasks`, then `/speckit-analyze` (and optionally `/speckit-checklist`) | Dependency-ordered `tasks.md` plus a consistency report. | ⛔ |
| 5 | `/speckit-implement` | Executes the tasks. Each task is checked off in `tasks.md` and committed. | |
| 6 | `/speckit-converge` | Appends any unbuilt work as new tasks. Repeat 5–6 until "converged". | |
| 7 | Verification (see the feature's `quickstart.md`) | Tests, lint, and a demo on the Android emulator and iOS simulator. | ⛔ |

After acceptance, the feature branch is merged into `kmp` with `git merge --no-ff`.

**Bugs** follow the same loop: a small spec describing expected vs. actual behaviour, then plan, tasks and implement.

### Rules

- Specs describe **what and why**; plans describe **how**. Never put technology choices in `spec.md`.
- Any behaviour change starts by updating the spec. Specs are living documents.
- Every technical decision with alternatives gets an ADR entry in the feature's `research.md`, with
  primary-source citations.
- Keep `tasks.md` checkboxes truthful. They are the durable progress record.
- Never skip a ⛔ gate, even when resuming automatically.

### Resuming work (after a usage-limit reset, a restart, or a new session)

1. `git status`, `git branch --show-current`, `git log --oneline -10`.
2. Open the active feature's `specs/NNN-slug/tasks.md`. Find the first unchecked task and check
   whether the last commit already covers it.
3. Continue from there. If the last completed step precedes a ⛔ gate, stop and ask for review instead.

Usage limits: Claude Code auto-continues after a session limit resets (`autoContinueAtUsageLimit`).
In Remote Control sessions, run `/rate-limit-options` → "Wait here, then continue automatically".
Do **not** schedule cron/wakeup watchdogs for this.

## 4. Architecture rules (summary — see the constitution and ADRs)

- **Shared brain, thin native UIs.** All of the following live in `shared`:
  - domain logic and state machines;
  - ViewModels;
  - user-facing strings (EN/ES);
  - TTS orchestration;
  - persistence.

  UIs only render state and forward user actions.
- **commonMain is platform-free.** Every dependency must also support `jvm` and `wasmJs`, so desktop,
  web and Compose Multiplatform can be added without rewrites.
- **MVI-style unidirectional data flow, per screen**, in `presentation/<screen>/`:
  - `XState`: an immutable data class with defaults;
  - `XAction`: a sealed interface;
  - `XEvent`: a sealed interface for one-off events, sent through a `Channel` and exposed with `receiveAsFlow()`;
  - `XViewModel`: exposes `state: StateFlow<XState>`, `events: Flow<XEvent>` and `onAction(XAction)`.
- **Business rules are plain Kotlin** (pure reducers and use cases, with injected `Random` or
  clock). ViewModels are thin adapters over them.
- **ViewModels** extend `androidx.lifecycle.ViewModel`, from the
  `org.jetbrains.androidx.lifecycle:lifecycle-viewmodel` artifact, in commonMain (see ADR-001 in
  spec 001's `research.md`).
  - iOS never sees lifecycle types or generics. Swift asks the Kotlin `ViewModelProvider` for a
    ViewModel scoped to a non-generic `ScreenScope`, and closes the scope when it's done.
- **The `ScreenRoot` / `Screen` split** applies on both platforms:
  - `ScreenRoot` is stateful: it obtains the ViewModel, collects state and events, and handles navigation.
  - `Screen` is stateless: it takes `state` plus `onAction`, and has previews.
  - Android collects with `collectAsStateWithLifecycle` and `ObserveAsEvents`.
  - iOS creates the ViewModel inside `.task`, iterates with `for await`, switches on sealed types with
    `onEnum(of:)` (SKIE), and closes the scope when the task is cancelled.
- **Package layout:** feature-first, `dev.epool.waay.<feature>.{data,domain,presentation}`, plus
  `core` and `di`.
- **Modules:** start with a single `shared` module. Split into Gradle modules and `build-logic`
  convention plugins only when a documented trigger happens, such as adding web, desktop or `sharedUI`.
- **DI:** Koin.
  - `sharedModule` plus `expect val platformModule`, wired by `initKoin()`.
  - Android uses `koinViewModel()`.
  - iOS uses the Swift-facing `ViewModelProvider`.
- **Swift interop:** SKIE.
  - Flows become `AsyncSequence`.
  - Sealed types become Swift enums.
  - `suspend` functions become `async`.
- **Swift-friendly APIs:**
  - explicit API mode in `shared`;
  - no generics on Swift-facing types;
  - small public surface.
- **Other libraries:**
  - logging: Kermit;
  - settings: multiplatform-settings.

## 5. Conventions

- **Identifiers:** `dev.epool.waay` (Android `applicationId`, iOS bundle id, Kotlin root package).
  Never `mx.eduardopool`.
- **Versions** live only in `gradle/libs.versions.toml`. Use the newest *mutually compatible* stable
  set, checked against the Kotlin compatibility guide (KGP ↔ Gradle/AGP/Xcode). Record the matrix in
  `research.md`.
- **Kotlin:** official code style, enforced by Spotless + ktlint (+ compose-rules). Use explicit API
  mode in `shared`.
- **Swift:** `swift format` (bundled with Xcode). SwiftUI with the Observation framework (iOS 17+).
- **Tests:**
  - Tests go first, in `commonTest`, using `kotlin.test`, `kotlinx-coroutines-test` and Turbine.
  - Fakes over mocks; seeded `Random` for determinism.
  - One UI smoke test per platform: Compose UI test and XCUITest.
- **Xcode project:** edit `iosApp/project.yml` and run `xcodegen`. Never hand-edit `project.pbxproj`.
- **Git:**
  - Use Conventional Commits (`feat:`, `fix:`, `docs:`, `build:`, `test:`, `refactor:`, `chore:`), in small commits.
  - Commit locally only. **Never `git push`** unless the human explicitly asks.
  - Never rewrite published history.
- **Language:** code, comments and docs in English. In-app strings in English and Spanish.

## 6. Tooling and commands

**Prerequisites:**
- JDK 21: Gradle toolchains handle the rest.
- Xcode, selected with `xcode-select`.
- Android SDK.
- Android CLI (`android`, in `~/.local/bin`).
- `uv` and `specify` (Spec Kit).
- `xcodegen`.

**Commands:**

```sh
./gradlew --version                     # Gradle wrapper (never install Gradle globally)
android info | android docs search "<q>" | android sdk list
android emulator start <avd> && android run --apks=<apk>   # see the android-cli skill
xcodegen --spec iosApp/project.yml      # regenerate the Xcode project
specify check                           # Spec Kit health
```

Build, test and lint commands are added here by spec 001's tasks once the modules exist. Expected:
- `./gradlew spotlessCheck lint allTests koverVerify`
- `./gradlew :androidApp:assembleDebug`
- `xcodebuild test -project iosApp/iosApp.xcodeproj -scheme Waay -destination 'platform=iOS Simulator,name=<device>'`

**Official guidance sources, to consult before inventing patterns:**
- `android docs search/fetch`, the official Android Knowledge Base, including the architecture recommendations.
- The official Android skills in `.claude/skills/`.
- The JetBrains `kotlin-agent-skills` plugin, e.g. `kotlin-tooling-agp9-migration` for the
  KMP + AGP 9 module structure and `kotlin-tooling-native-build-performance`.
